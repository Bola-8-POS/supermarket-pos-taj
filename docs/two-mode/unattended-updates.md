# Unattended updates of the store server

## What happens each night
Every hour the server asks the update feed whether a newer backend pack exists. If it does, and the store is **not trading** (no open caja, no sale in the last 30 minutes), it updates itself in a few minutes. Tills show "The store server is updating" and wait; no sale is lost.

The update runs only inside a local-time window, 01:00 to 05:00 by default (`maintenance.window` in `conf\posctl.json`, for example `{"start":"22:00","end":"06:00"}`; it may wrap midnight). The hourly check outside the window first finishes or undoes any interrupted update (recovery is never held to the window), and then only looks at the feed and remembers that a newer pack is waiting (so the pending-update alert still ages); `posctl update --window-aware` answers `OUTSIDE_WINDOW` and changes nothing, and the next hour inside the window goes ahead. The window bounds when the FENCE starts, not only when the run starts: the clock is checked when a scheduled run begins and again just before it takes the operation lock, so a run that spent its time resolving and downloading the pack and finds the window closed answers `OUTSIDE_WINDOW` and changes nothing (the downloaded pack stays installed for the next window). Once the fence is up it is not cut short: one that fences at 04:59 may run its maintenance budget (15 minutes by default) past 05:00. A window that cannot be read (for example `1:00`, an en dash, `25:00`, start equal to end, or a window with no whole hour in it such as `03:15`-`03:45`, because the check runs on the hour and would never fire inside it) falls back to 01:00-05:00 and raises the `MAINTENANCE_WINDOW_INVALID` alert; a 24-hour window cannot be written, leave `maintenance.window` out to get the default. A person who runs `posctl update` by hand is not held to the window.

An update never starts without a fresh backup. If the backup service is not available, the update is refused (`BACKUP_UNAVAILABLE`) and nothing is changed.

## The order that keeps tills safe
1. The **server** updates first (the scheduled task, or an administrator running `posctl update`).
2. Each **till** then installs the matching app update. A till refuses to install an app version that is newer than the server's pack, and a till whose app level differs from the server's schema level will not sell: it shows "This till needs an update" or "The store server has not been updated yet".
3. With no internet, deliver the pack and the app installer by USB and install **the server first, then the tills**.

A till that missed a release may wait until the next nightly server update before it can sell again; an administrator can run `posctl update` on the server to shorten that.

## If something fails
* The old version is restored automatically, the failed copy is kept for 7 days as `pos_failed_<time>`, and the server status shows the reason. Tills keep working on the old version.
* `posctl status` (and `status.json`) showing `"state": "recovery-needed"`, together with the `RECOVERY_NEEDED` alert, means the server was interrupted (a crash, a power cut, a reboot in the middle of an update) or could not roll back; tills stay on the "updating" screen until it is recovered. **Recovery is never held back by time**: while a journal is open the store is already down, so the scheduled tasks try to finish or undo the update as soon as they run, however long ago it began (a power cut over a weekend included) and whether or not the maintenance window is open. The recovery at boot (`posctl update --recover --quiet --scheduled`) and the hourly check both do this FIRST, before they look at the window. What bounds it is the number of attempts: after three failed attempts by the scheduled tasks (`RECOVERY_ATTEMPTS_EXHAUSTED`, alert `RECOVERY_SUPPORT_NEEDED`) they stop and change nothing more; call support, `status.json` shows `update.recoverAttempts`. A run that is refused before it starts (another operation holds the lock, no journal, an earlier refusal) is not an attempt and does not use one up. Each single database statement is still capped at 10 minutes. The scheduled tasks carry a hidden `--scheduled` flag; that flag alone marks a run as unattended. Anything you type yourself, with or without `--quiet`, is a run by hand: use plain `posctl update --recover` on the server PC (as Administrator). It is allowed at any time, also after the scheduled tasks gave up, and it does not use up or reset their three attempts. If it still reports `RECOVERY_NEEDED`, send the files in `C:\ProgramData\SupermarketPOS\logs\posctl\ops\` and `state\update\journal.json` to support. Do not delete the journal.
* Not enough free disk space is reported as `DISK_SHORT` with the amount needed and the amount free; free some space and run the update again.
* If the maintenance budget (15 minutes by default) is used up, the update stops before changing anything or rolls back (`MAINTENANCE_BUDGET`). The budget only stops a new phase from starting: once the live check has passed the update is committed, whatever the clock says.
* After the tills were let back in, an update is never undone automatically. Restore from the pre-update backup only on support's instruction.

* **A version that rolled back is not retried every night.** The pack version that rolled back is written to `state\update\update-rolled-back.json`. While that version is still the newest one available, the scheduled check skips it: it exits 0 with reason `SKIPPED_ROLLED_BACK`, fences nothing, writes no journal and uses up no recovery attempt. `status.json` carries the warn alert `UPDATE_ROLLED_BACK` and `update.rolledBackVersion` for as long as the record exists. As soon as a newer pack appears the scheduled check takes it and the record is replaced or cleared. To retry the same version yourself, run `posctl update` (without `--scheduled`, as Administrator) once the cause is fixed; a successful update clears the record and the alert. Only a failure the version itself causes parks it: a failed migration (14), a failed verification (15), the maintenance budget run out, or a crash or kill inside the version's own work (the recovery that rolls it back writes the record too). A fence failure, a failed backup, a failed clone, a refused precondition or the window never park it; the next window tries again and `update.lastCode` / `lastReason` say what happened. A recovery that could not roll back (`RECOVERY_NEEDED`) is a different case and writes no such record until it does roll back; a recovery that completes the update (rolls forward) clears the record.
* `status.json` `update.lastCode` (the numeric exit code of the last update, for example 0, 14, 15) and `update.lastReason` (its reason, for example `VERIFY_FAILED`) say what happened without opening `state\update\update-result.json`.
* **The updater's own files are for administrators only.** The journal, the lock, `update-result.json`, `update-rolled-back.json` and the service start-type record live in `state\update\`, which only SYSTEM and Administrators can open (`state\` itself is readable by the gateway for `status.json`). Run `posctl update`, `posctl update --recover` and `posctl status` elevated. Without elevation `update` and `start`/`stop`/`restart` refuse with exit 17 ("run the command elevated"), and `posctl status` reports the state as `unknown` with the warn alert `UPDATE_STATE_UNKNOWN` instead of claiming that no update is running. A store updated from an older posctl keeps these files in `state\` until the first update or recovery moves them.

* **Out-of-date scheduled tasks (`TASKS_STALE`).** The Health check (every minute) reads the `Recover` and `UpdateCheck` tasks and checks that each one exists, that its action arguments contain `--scheduled` and that its `ExecutionTimeLimit` is the one this build installs (a task without the element counts as stale). A task that is missing, or that an older posctl installed without the flag or with a shorter limit, raises the warn alert `TASKS_STALE` ("run posctl tasks install"); a run from such a task would be counted as a person's. `status.json` `tasksCurrent` is `true` when both are current, `false` when one is not, and `null` when the Task Scheduler could not be read (unknown is never reported as current, and raises no alert). Fix: run `posctl tasks install` as Administrator; the alert clears at the next Health run.
* **The PC stays awake while an update or a recovery runs, and the scheduled tasks have limits derived from the code's own timeouts.** From the moment an update takes the lock (or a recovery starts) until it ends, by success, rollback, error or crash of the process, `posctl` holds Windows' "system required" state so the PC cannot go to sleep in the middle of a fence; it is released on every way out. The Task Scheduler limits are computed in `store-server/src/update/limits.rs` and a test fails if a limit falls below them. **Recover** may run at most the boot lock retries plus one recovery attempt, taken at its longest branch: a journal past the swap that resumes forward and fails in `verify_live`, then rolls back (re-fence and find the databases, re-activate the new pack, 2 collation statements, start the stack, `verify_live` with 3 statements at the 10-minute cap, four 5-second probes and the 2-minute lockout canary, then a full service cycle and 12 statements at the 10-minute cap), 250 minutes with a 10-minute margin. **UpdateCheck** may run either a recovery or a whole update, whichever is longer, because a scheduled run that recovered an interrupted operation stops there (reason `RECOVERED`) and the next hourly run does the update; a hand `posctl update` that meets a journal still recovers and updates in one run. The update side is the pack install and feed fetch timeouts (15 and 30 minutes), 8 prechecks at the 10-minute cap, the 2-minute lock wait, the maintenance budget at its runtime ceiling of 60 minutes (the configuration accepts up to 120, the run clamps to 60), one statement of overshoot, and a rollback reserve (a full service cycle and 12 statements at the 1-minute floor); it is the larger of the two, 249 minutes with the margin (here the recovery, at 239 minutes, is the larger). The statement counts (12, 8, 3 and 2) are estimates from reading the code, not measurements. These are ceilings for a wedged machine, not durations: a normal update takes minutes. A machine that already has the tasks picks the new limits up when `posctl tasks install` runs, which the installer does on every app install; until then a task still carrying an older `ExecutionTimeLimit` (compared as a duration, so `PT2H33M` equals `PT153M`) is reported as `TASKS_STALE` like a missing `--scheduled` flag.
* After any manual install repair, run `posctl tasks install`.

## About the migration SQL scan
The statement scan that refuses cluster-level SQL in a pack (roles, `COPY .. PROGRAM`, server-side `COPY` files, `lo_import`/`lo_export`, `CREATE EXTENSION`) is a lint, not a security boundary. The real controls are `NOSUPERUSER` on the migration role and the cluster digest check before and after the work. The CI test exempts exactly two historical migrations from the `CREATE EXTENSION` rule (`20260506000002_agent_rag_schema.sql`, `20260807000001_pool_session_atomic_rpcs.sql`), pinned by filename and content hash; the runtime scan has no exemption. Both predate the base and are applied by provisioning, never by the updater; a store on a base that old is an owner-handled case.

## Where to look
`state\update\update-result.json` (last result, pending update), `logs\posctl\ops\` (one log per step), `posctl status`.
